# ร่างข้อตกลงและกติกา Freelink Escrow (ฉบับละเอียด)

Nov 17, 2026 · @Rawiphas Callhim

## เอกสารนี้คืออะไร

เอกสารนี้รวมกติกาทั้งหมดของ Freelink Escrow ว่าผู้จ้างกับฟรีแลนซ์ต้องทำอะไรบ้าง ถ้าใครไม่ทำจะเกิดอะไรขึ้น และถ้าตกลงกันไม่ได้ใครเป็นคนตัดสิน ใช้กับ demo บน Sepolia ไม่ต้องครบระดับใช้งานจริง แต่แนวคิดต้องถูก

ตัวเลขตั้งต้นทั้งหมดมาจาก `contracts/FreelinkEscrow.sol` (v2): ค่าธรรมเนียม 5% ผู้จ้างมีเวลาตรวจงาน 7 วัน ฟรีแลนซ์มีเวลาแก้งาน 7 วัน ขอแก้ได้ 2 ครั้ง และคนตัดสินมีเวลา 14 วัน

ในเอกสารจะเจอคำว่า "มีแล้ว" กับ "เสนอ" บ่อย "มีแล้ว" คือโค้ดตอนนี้ทำแบบนั้นอยู่ ส่วน "เสนอ" คือยังไม่ได้ทำ และยังไม่ได้ตกลงกัน

## 1. หลักคิดเบื้องหลังกติกา

กติกาทุกข้อในเอกสารนี้มาจากหลัก 7 ข้อนี้ ถ้าเจอกรณีที่ไม่ได้เขียนไว้ ให้กลับมาดูหลักพวกนี้

1. **contract คุมได้แค่เงินกับเวลา** มันบังคับให้ใครทำงานหรือกดปุ่มไม่ได้ และดูไม่ออกว่างานดีหรือไม่ดี เรื่องคุณภาพงานจึงต้องให้คนตัดสินดูจากหลักฐาน
2. **รอใครอยู่ก็ต้องมีวันหมดเวลา** ถ้าฝ่ายหนึ่งเงียบ อีกฝ่ายต้องรอให้ถึงเวลาแล้วเอาเงินออกเองได้เสมอ เงินต้องไม่ติดอยู่ใน contract ตลอดไป ตอนนี้ทำได้ครบแล้ว หลังปิดช่องโหว่ returndata bomb ในข้อ 6
3. **ยอมเสียเปรียบเองได้เสมอ แต่จะทำให้อีกฝ่ายเสียเปรียบต้องมีเงื่อนไข** เช่น ผู้จ้างยอมจ่าย ฟรีแลนซ์ยอมคืนเงิน หรือผู้จ้างยอมขยายเวลาให้ พวกนี้กดคนเดียวได้เลย แต่การดึงเงินคืนหรือการเบิกเงินต้องรอเวลา หรือให้อีกฝ่ายยินยอมก่อน
4. **ถ้าทุกคนเงียบ คนผิดต้องได้ประโยชน์น้อยที่สุด** contract ไม่รู้ว่าใครผิด สิ่งที่ทำได้คือจำกัดไม่ให้คนโกงได้กำไรมาก (รายละเอียดอยู่ใน D2 ข้อ 11)
5. **ไม่มีใครแตะเงินนอกกติกาได้ รวมถึงเจ้าของแพลตฟอร์ม** และกติกาของงานที่เริ่มไปแล้วจะไม่เปลี่ยนกลางทาง ข้อนี้มีแล้ว
6. **ของที่อยู่บน chain ทุกคนเห็นตลอดไป** จึงเก็บบน chain แค่ตัวเลขกับ hash ส่วนข้อความจริงและไฟล์เก็บไว้ที่แพลตฟอร์ม
7. **คนตัดสินต้องไม่ได้อะไรจากผลตัดสิน** ตอนนี้กันไว้แล้วว่าคนตัดสินต้องไม่ใช่คู่กรณี ส่วนเรื่องเงิน ตกลงแล้วว่าไม่เก็บค่าธรรมเนียมจากงานที่จบด้วยคำตัดสิน เจ้าของซึ่งเป็นคนตัดสินจึงไม่ได้อะไรเพิ่มไม่ว่าจะตัดสินให้ใคร (D1 และ D3)

## 2. ใครทำอะไร

ในระบบมี 6 บทบาท เจ้าของแพลตฟอร์มเป็นคนตัดสินเอง และมี wallet สำรองของทีมไว้ตัดสินแทนเมื่อเจ้าของเงียบ ถ้าไม่ได้ตั้งค่าใน `.env` สคริปต์ deploy จะใช้ wallet เดียวกันทั้งหมด ซึ่งใช้ได้สำหรับเจ้าของกับคนรับค่าธรรมเนียม แต่ wallet สำรองต้องเป็นคนละ wallet กับเจ้าของ

- **ผู้จ้าง (client)** เป็นคนฝากเงิน ยกเลิกได้ถ้าฟรีแลนซ์ยังไม่รับงาน กดจ่ายได้ ขอแก้ได้ตามจำนวนรอบที่ตกลง เปิดข้อพิพาทได้ และขอเงินคืนได้ถ้าเลย deadline แล้วยังไม่มีงานส่งมา หน้าที่คือตรวจงานให้เสร็จใน 7 วัน ตรวจตามรายการที่ตกลงกันไว้ และไม่เอางานไปใช้จริงก่อนจ่าย สิ่งที่ห้ามทำคือขอของนอกข้อตกลงแล้วอ้างว่างานไม่ครบ
- **ฟรีแลนซ์ (freelancer)** เลือกได้ว่าจะรับงานหรือไม่ ยกเลิกแล้วคืนเงินผู้จ้างได้ทุกเมื่อ เบิกเงินเองได้ถ้าผู้จ้างไม่ตรวจงานภายใน 7 วัน และเปิดข้อพิพาทได้ก่อนถึง deadline ก่อนรับงานต้องเช็กยอดเงิน deadline และข้อตกลงให้ตรงกัน งานที่ส่งต้องตรงกับ hash ที่ส่งขึ้น chain และห้ามส่งงานปลอม ลอกงาน หรือชวนผู้จ้างไปจ่ายนอกแพลตฟอร์ม
- **เจ้าของแพลตฟอร์ม (owner) ซึ่งเป็นคนตัดสิน (arbiter) ด้วย** คือคนที่ deploy contract ตั้งค่าธรรมเนียมได้ไม่เกิน 10% เปลี่ยนคนตัดสินและ wallet รับค่าธรรมเนียมได้ แต่แตะเงินที่ฝากไว้ไม่ได้ เพราะ contract ไม่มีช่องให้ทำ ในฐานะคนตัดสิน แบ่งเงินได้ตั้งแต่ 0 ถึง 100% ต้องตัดสินภายใน 7 วันและส่งเหตุผลให้ทั้งสองฝ่าย ห้ามตัดสินงานที่ตัวเองเป็นคู่กรณี และต้องแจ้งผู้ใช้ก่อนเปลี่ยนการตั้งค่า
- **wallet สำรองของทีม** ตัดสินข้อพิพาทแทนได้หลังวันที่ 7 ถ้าเจ้าของยังเงียบ ทำอย่างอื่นไม่ได้ ถูกล็อกไว้ตั้งแต่ตอนฝากเงินเหมือนคนตัดสิน (D4)
- **wallet รับค่าธรรมเนียม (feeRecipient)** รับ 5% ของค่าจ้างที่จ่ายออกไปจริง เป็น wallet เดียวกับเจ้าของได้ เพราะงานที่จบด้วยคำตัดสินไม่เก็บค่าธรรมเนียม
- **ตัวแพลตฟอร์ม (backend และหน้าเว็บ)** ผูก escrow เข้ากับงานในฐานข้อมูล เก็บต้นฉบับข้อตกลงและหลักฐาน แจ้งเตือนก่อนถึงทุก deadline และแบนบัญชีได้ แต่ต้องไม่ถือเงินแทนผู้ใช้ และต้องเช็กกับ chain ทุกครั้งก่อนเชื่อข้อมูลที่ผู้ใช้ส่งมา

คนนอกที่ไม่เกี่ยวข้องทำได้แค่เปิด escrow ของตัวเองและอ่านข้อมูลสาธารณะ แตะ escrow ของคนอื่นไม่ได้

## 3. ใครบังคับกติกาส่วนไหน

กติกาไม่ได้ถูกบังคับด้วย contract อย่างเดียว แต่มีอยู่ 4 ชั้น ชั้นแรกบังคับได้แน่นอนที่สุดแต่ทำได้น้อยที่สุด เรื่องไหนชั้นแรกจัดการไม่ได้ก็ส่งต่อไปชั้นถัดไป

1. **contract** บังคับได้เด็ดขาด ไม่มีใครฝ่าฝืนได้ แต่คุมได้แค่ว่าใครกดอะไรได้ตอนไหน เงินไปทางไหน และหมดเวลาแล้วเกิดอะไร คุณภาพงานหรือเรื่องที่เกิดนอก chain มันมองไม่เห็น
2. **แพลตฟอร์ม** คุมได้ว่าใครเห็นงานไหน ส่งแจ้งเตือน ให้คะแนนชื่อเสียง และแบนบัญชี แต่เงินที่เข้า escrow ไปแล้ว แพลตฟอร์มก็แตะไม่ได้
3. **คนตัดสิน** ดูเนื้องานแล้วแบ่งเงินตามสัดส่วน แต่แบ่งได้แค่เงินที่อยู่ใน escrow ถ้าความเสียหายมากกว่าค่าจ้างก็ช่วยไม่ได้
4. **ข้อตกลงการใช้งาน (ToS) และกฎหมาย** ใช้กับเรื่องลิขสิทธิ์ ความลับ การโกง หรือความเสียหายที่เกินค่าจ้าง แต่ถ้าผู้ใช้ไม่เปิดเผยตัวตนก็ตามตัวไม่ได้

สิ่งที่ต้องเข้าใจคือ contract แบนใครไม่ได้ คนที่โดนแบนจากแพลตฟอร์มยังเรียก contract ตรง ๆ ได้ แค่ backend จะไม่เอา escrow นั้นมาผูกกับงานในระบบ

สำหรับ demo ชั้นที่ 4 ทำแค่หน้าให้ผู้ใช้กดยอมรับข้อตกลงก่อนฝากเงินและก่อนรับงานก็พอ เนื้อหาในหน้านั้นก็คือกติกาในเอกสารนี้

## 4. ข้อตกลงงาน

ข้อตกลงงานคือสิ่งที่คนตัดสินใช้เทียบเวลามีข้อพิพาท จึงต้องเขียนให้ตรวจได้จริง และต้องผูกกับตัวเลขบน chain ด้วย ตอนนี้ `buildTermsHash` ในหน้าเว็บเอาแค่ projectId, jobId, ชื่องาน และงบเป็นบาทมา hash ยังไม่รวมยอดเงินจริง deadline address หรือรายการตรวจรับ

### 4.1 ข้อตกลงต้องมีอะไรบ้าง

| ฟิลด์ | เก็บอะไร และเก็บไว้ทำไม |
| --- | --- |
| `v` | เลขเวอร์ชันของรูปแบบ ถ้าวันหลังเปลี่ยนสูตรจะได้ไม่ปนกับของเก่า |
| `chainId`, `contract` | เครือข่ายและ address ของ contract กันไม่ให้เอา hash เดียวกันไปใช้ที่อื่น |
| `projectId` | ผูกกับงานในฐานข้อมูล |
| `client`, `freelancer` | address ของผู้จ้างและฟรีแลนซ์ |
| `amountWei`, `deadline` | ยอดเงินและ deadline ต้องตรงกับที่ฝากจริง |
| `scope` | ขอบเขตงานเป็นข้อความ |
| `deliverables` | สิ่งที่ต้องส่ง เช่น source code และลิงก์ทดลองใช้ |
| `checklist` | รายการตรวจรับ (4.2) |
| `revisionPolicy` | แก้ได้กี่รอบ และอะไรนับเป็นการแก้ (4.3) |
| `ip` | ลิขสิทธิ์โอนให้ผู้จ้างเมื่อไหร่ (ข้อ 10) |
| `confidential` | เป็นงานลับหรือไม่ ถ้าใช่ ฟรีแลนซ์เอาไปลงผลงานไม่ได้ |
| `tosVersion` | ToS ฉบับที่ทั้งสองฝ่ายกดยอมรับ |

### 4.2 รายการตรวจรับ

ผู้จ้างไม่ต้องให้คะแนนหรือคิดน้ำหนักอะไร แค่อ่านว่าจะได้อะไร แล้วตอนตรวจงานก็ลองกดทีละข้อว่าใช้ได้หรือไม่ได้ งาน dev ทำแบบนี้ได้เพราะซอฟต์แวร์ลองใช้ดูได้เลยโดยไม่ต้องอ่านโค้ด ส่วนการคิดเป็นเงินเป็นหน้าที่ของคนตัดสิน (8.3)

วิธีทำงานเป็นแบบนี้

- ผู้จ้างเขียนโจทย์คร่าว ๆ ตอนประกาศงานเหมือนเดิม แล้วฟรีแลนซ์เป็นคนแปลงโจทย์เป็นรายการตรวจรับในข้อเสนอ เพราะเขารู้ว่าอะไรทำได้ หน้าเว็บแสดงโจทย์กับรายการไว้คู่กัน ถ้ามีอะไรที่ผู้จ้างอยากได้แต่ไม่อยู่ในรายการ ผู้จ้างจะเห็นและทักได้ก่อนฝากเงิน
- แต่ละข้อเขียนในรูป "ผู้ใช้ทำ … ได้" ห้ามใช้คำที่วัดไม่ได้อย่าง "สวย" "เร็ว" หรือ "ใช้ง่าย" ถ้าจำเป็นต้องพูดเรื่องความเร็วก็ใส่ตัวเลข เช่น "หน้าแรกโหลดไม่เกิน 3 วินาที"
- แต่ละข้อเป็นแค่ "ต้องมี" หรือ "เสริม" ไม่มีตัวเลขน้ำหนัก
- แพลตฟอร์มเติมข้อมาตรฐานให้ทุกงานเอง ผู้จ้างไม่ต้องรู้ว่าต้องขอ ได้แก่ ส่ง source code ครบพร้อมวิธีติดตั้ง มีลิงก์ทดลองใช้ (หรือไฟล์ติดตั้งถ้าเป็นแอปมือถือ) และไม่ฝังรหัสผ่านหรือ API key ไว้ในโค้ด

ตัวอย่างรายการของงานเว็บร้านค้าออนไลน์

| ข้อ | ระดับ | ผู้จ้างตรวจยังไง |
| --- | --- | --- |
| สมัครสมาชิกและล็อกอินด้วยอีเมลได้ | ต้องมี | สมัครด้วยอีเมลตัวเอง |
| หยิบสินค้าใส่ตะกร้าและสั่งซื้อได้ | ต้องมี | ลองสั่ง 1 ชิ้น |
| แอดมินเพิ่ม แก้ และลบสินค้าได้ | ต้องมี | ล็อกอินด้วยบัญชีแอดมินที่ได้รับ |
| เปิดบนมือถือแล้วไม่ล้นจอ | ต้องมี | เปิดลิงก์บนมือถือ |
| ค้นหาสินค้าด้วยชื่อได้ | เสริม | พิมพ์ชื่อสินค้าในช่องค้นหา |
| ส่งอีเมลยืนยันหลังสั่งซื้อ | เสริม | ดูกล่องอีเมลหลังสั่ง |
| มีลิงก์ทดลองใช้ (แพลตฟอร์มเติมให้) | ต้องมี | กดลิงก์ |
| ส่ง source code ครบพร้อมวิธีติดตั้ง (แพลตฟอร์มเติมให้) | ต้องมี | เห็นว่ามีไฟล์ ส่วนรันได้จริงไหม คนตัดสินเป็นคนตรวจ |

ตอนตรวจงาน ผู้จ้างกด "ใช้ได้" หรือ "ใช้ไม่ได้" ทีละข้อ ถ้าจะขอแก้ก็เลือกข้อที่ไม่ผ่าน ห้ามใช้ "ผู้จ้างพอใจ" เป็นเงื่อนไข เพราะวัดไม่ได้ และผู้จ้างจะปฏิเสธงานได้ทุกครั้ง

### 4.3 แก้งาน กับ งานใหม่ ต่างกันยังไง

ถ้าข้อที่อยู่ในรายการยังใช้ไม่ได้ (บั๊ก) หรือผู้จ้างขอปรับรายละเอียดเล็ก ๆ ในขอบเขตเดิม นั่นคือ **การแก้งาน** ฟรีแลนซ์ต้องทำให้โดยไม่คิดเงินเพิ่ม

ถ้าผู้จ้างขอของที่ไม่อยู่ในรายการ ขอเปลี่ยนข้อเดิม หรือเปลี่ยนแนวทางทั้งหมด นั่นคือ **งานใหม่** ต้องเปิด escrow ใหม่และจ่ายเพิ่ม ถ้าผู้จ้างขอของแบบนี้มาในชื่อการแก้งานแล้วฟรีแลนซ์ไม่ทำ ไม่ถือว่าฟรีแลนซ์ผิดสัญญา

contract นับได้แค่ว่าผู้จ้างกด "ขอแก้" ไปกี่ครั้ง แยกไม่ออกว่าแก้เล็กหรือใหญ่ จำนวนรอบจึงมีไว้กันเงินถูกล็อกไม่จบ ไม่ได้มีไว้วัดคุณภาพ เพราะแต่ละรอบทำให้งานยืดไปอีกราว 14 วัน กติกาที่ตกลงแล้วคือ

- 1 รอบ = ผู้จ้างส่งงานกลับ 1 ครั้ง โดยติ๊กข้อที่ไม่ผ่านทั้งหมดพร้อมกัน
- จำนวนรอบตกลงกันในข้อตกลงของแต่ละงาน ได้ 0 ถึง 5 รอบ ค่าเริ่มต้น 2 รอบ และบันทึกลง contract ตอนฝากเงิน
- ฟรีแลนซ์กด "ให้รอบแก้เพิ่ม" เองได้ทีละรอบถ้ายอมแก้ต่อ ทำคนเดียวได้ เพราะคนที่เสียเปรียบคือตัวเขาเอง (หลักข้อ 3)
- ครบรอบแล้วยังไม่ผ่าน ผู้จ้างเลือกได้ว่าจะกดจ่าย หรือเปิดข้อพิพาทให้คนตัดสินแบ่งเงินตามระดับใน 8.3 ผู้จ้างจึงไม่ต้องจ่ายเต็มให้งานที่ใช้ไม่ได้
- บั๊กที่เจอหลังจ่ายเงินแล้ว contract ช่วยไม่ได้เพราะเงินออกไปแล้ว เสนอให้ใส่ระยะรับประกันในข้อตกลง เช่น แก้บั๊กฟรี 14 วัน ถ้าไม่ทำโดน strike

### 4.4 การคำนวณ termsHash

termsHash คือ keccak256 ของข้อตกลงในรูป JSON ที่เขียนแบบเดียวกันทุกครั้ง คือเรียง key ตามตัวอักษร ไม่มีช่องว่าง ใช้ UTF-8 แบบ NFC และเก็บตัวเลขเงินเป็น string backend เป็นคนสร้างและเก็บต้นฉบับไว้ให้ทั้งสองฝ่ายดาวน์โหลดได้ ส่วนหน้าเว็บต้องคำนวณ hash ซ้ำจากข้อความที่แสดงให้ผู้ใช้เห็นจริง ไม่เชื่อ hash ที่ server ส่งมา

### 4.5 ฟรีแลนซ์ต้องเช็กอะไรก่อนรับงาน

ก่อนกดรับงาน หน้าเว็บต้องอ่านยอดเงิน ค่าธรรมเนียม และ deadline จาก `getEscrow` มาเทียบกับข้อตกลงให้ฟรีแลนซ์เห็น รวมถึงจำนวนรอบแก้ และคนตัดสินกับ wallet สำรองที่ถูกล็อกไว้ตอนฝาก (D4)

contract เช็กเองด้วยแล้ว ผ่าน `acceptEscrow(escrowId, termsHash, expectedAmount, expectedDeadline)` เพราะ contract อ่าน JSON ไม่ได้ ถ้าเทียบแค่ termsHash จะไม่รู้ว่ายอดเงินกับ deadline ตรงหรือไม่

### 4.6 แบ่งจ่ายเป็นงวด

งานใหญ่แบ่งจ่ายเป็นงวดได้โดยไม่ต้องแก้ contract เพราะแต่ละงวดคือ escrow แยกกัน ใช้ projectId ต่อท้ายด้วยเลขงวด เช่น prj\_123-m1 ส่วนลำดับและสัดส่วนเงิน แพลตฟอร์มเป็นคนคุม

- แต่ละงวดมีรายการตรวจรับของตัวเอง
- ทำทีละงวดตามลำดับ ผู้จ้างฝากเงินงวดถัดไปได้หลังรับงานงวดก่อนแล้วเท่านั้น
- งวดแรกได้ไม่เกิน 30% ของทั้งงาน และงวดสุดท้ายต้องไม่ต่ำกว่า 30% ฟรีแลนซ์ที่เลือกทำส่วนง่ายแล้วทิ้งงานจึงได้เงินไม่มาก
- งวดแรกควรเป็นแกนของงาน ไม่ใช่ส่วนที่ง่ายที่สุด ผู้จ้างเห็นลำดับงวดทั้งหมดก่อนกดยอมรับ
- ถ้าฟรีแลนซ์ทิ้งงานกลางทาง งวดที่จ่ายไปแล้วไม่ถูกดึงคืน งวดที่ค้างอยู่จบตามข้อ 7 และผู้จ้างไม่ต้องฝากงวดที่เหลือ

## 5. งานเดินไปยังไง

ทุกจังหวะที่ต้องรอใครสักคน มีผลตั้งต้นรอไว้แล้วถ้าคนนั้นไม่ทำ ด้วยค่าตั้งต้นตอนนี้ เงินของผู้จ้างอาจถูกล็อกนานสุดประมาณ deadline บวกอีก 49 วัน ถ้าตั้งรอบแก้ไว้ 2 รอบ (เพิ่มอีกรอบละ 14 วัน)

สถานะของ escrow มี 7 สถานะ (ไม่นับ Unfunded ที่ยังไม่มีการฝาก) ตารางนี้ทำจากโค้ดตอนนี้ แทนแผนภาพที่ส่งออกเป็นไฟล์ไม่ได้

| จาก | ไป | เกิดเมื่อ | ใครทำ |
| --- | --- | --- | --- |
| Funded | Active | รับงาน (`acceptEscrow`) | ฟรีแลนซ์ |
| Funded | Refunded | ยกเลิกหรือปฏิเสธงานก่อนรับ (`refundClient`) | ผู้จ้างหรือฟรีแลนซ์ |
| Active | Submitted | ส่งงานก่อน deadline (`submitWork`) | ฟรีแลนซ์ |
| Active | Released | กดจ่ายตั้งแต่ฟรีแลนซ์รับงาน (`releasePayment`) | ผู้จ้าง |
| Active | Refunded | เลย deadline และไม่เคยส่งงาน หรือฟรีแลนซ์ยอมยกเลิก (`refundClient`) | ผู้จ้างหรือฟรีแลนซ์ |
| Active | Disputed | เปิดข้อพิพาท (`openDispute`) | ผู้จ้าง หรือฟรีแลนซ์ก่อน deadline |
| Submitted | Released | กดจ่าย หรือเบิกเองเมื่อหมดช่วงตรวจรับ (`releasePayment`, `claimAfterReview`) | ผู้จ้าง / ฟรีแลนซ์ |
| Submitted | Active | ขอแก้งาน (`requestRevision`) ไม่เกินจำนวนรอบที่ตกลงไว้ | ผู้จ้าง |
| Submitted | Disputed | ปฏิเสธงานในช่วงตรวจรับ (`openDispute`) | ผู้จ้าง |
| Submitted | Refunded | ฟรีแลนซ์ยอมยกเลิก (`refundClient`) | ฟรีแลนซ์ |
| Disputed | Resolved | คนตัดสินสั่งแบ่งเงิน (`resolveDispute`) หรือหมดเวลาแล้วแบ่งครึ่ง (`settleExpiredDispute`) | คนตัดสิน / คู่กรณีคนใดคนหนึ่ง |
| Disputed | Released | ผู้จ้างยอมแพ้ ค่าธรรมเนียมคิดเต็ม (`releasePayment`) | ผู้จ้าง |
| Disputed | Refunded | ฟรีแลนซ์ยอมแพ้ (`refundClient`) | ฟรีแลนซ์ |

ที่ยังเป็นข้อเสนอและไม่มีในตาราง: ตกลงกันเองตอนพิพาทด้วย `proposeSettlement` (8.5) และ wallet สำรองของทีมตัดสินแทนหลังวันที่ 7 (D2)

1. **ตกลงงาน** ทั้งสองฝ่ายคุยกันบนแพลตฟอร์มจนได้ข้อตกลง ตอนนี้ยังไม่มีอะไรบน chain
2. **ผู้จ้างฝากเงิน** escrow อยู่ในสถานะ Funded และ termsHash ถูกบันทึกไว้
3. **ฟรีแลนซ์รับงาน** สถานะเปลี่ยนเป็น Active ถ้าฟรีแลนซ์ไม่ยอมรับสักที ผู้จ้างยกเลิกแล้วเอาเงินคืนได้ทุกเมื่อ
4. **ฟรีแลนซ์ส่งงาน** ภายใน deadline พร้อม workHash สถานะเป็น Submitted ถ้าเลย deadline แล้วไม่มีงานส่งมา ผู้จ้างขอเงินคืนเต็มได้
5. **ผู้จ้างตรวจงาน** มีเวลา 7 วัน จะกดจ่าย ขอแก้ หรือเปิดข้อพิพาทก็ได้ ถ้าเงียบจนหมดเวลา ฟรีแลนซ์เบิกเงินเองได้
6. **ขอแก้** ทำได้ระหว่างตรวจงาน ไม่เกินจำนวนรอบที่ตกลงไว้ (ค่าเริ่มต้น 2 รอบ) สถานะกลับไปเป็น Active และฟรีแลนซ์มีเวลาส่งงานแก้อย่างน้อย 7 วัน ถ้าไม่ส่ง ผู้จ้างต้องเปิดข้อพิพาท
7. **ข้อพิพาท** สถานะเป็น Disputed เจ้าของแพลตฟอร์มซึ่งเป็นคนตัดสินควรตัดสินให้เสร็จใน 7 วัน ถ้าไม่ตัดสิน wallet สำรองของทีมตัดสินแทนได้ ถ้าเงียบทั้งคู่ครบ 14 วัน เงินจะถูกแบ่งครึ่ง
8. **จบ** สถานะเป็น Released, Refunded หรือ Resolved แล้วแต่ว่าจบแบบไหน

ทุกขั้นมี event บน chain เป็นหลักฐาน เช่น EscrowFunded, WorkSubmitted และ DisputeResolved

ตัวเลข 49 วันมาจากกรณีที่แย่ที่สุด คือฟรีแลนซ์ส่งงานตรง deadline ผู้จ้างดึงเวลาตรวจจนวินาทีสุดท้ายแล้วขอแก้ 2 รอบ จากนั้นเปิดข้อพิพาทในรอบที่สาม และคนตัดสินเงียบ รวมเป็นเวลาตรวจ 3 รอบ (21 วัน) เวลาแก้ 2 รอบ (14 วัน) และเวลารอคนตัดสิน (14 วัน) หน้าเว็บควรบอกตัวเลขนี้ให้ผู้จ้างรู้ก่อนฝาก และแจ้งเตือนก่อนหมดเวลาทุกช่วง (เสนอที่ 72 และ 24 ชั่วโมง)

### ถ้าประกาศงานแล้วไม่มีคนรับ

ตอนประกาศงานยังไม่มีเงินถูกล็อก เพราะ `depositEscrow` ต้องใส่ address ฟรีแลนซ์ ผู้จ้างจึงฝากเงินได้หลังเลือกคนแล้วเท่านั้น ปัญหานี้เป็นเรื่องหาคน ซึ่งแพลตฟอร์มช่วยได้ 4 ทาง

- **ผู้จ้างเชิญฟรีแลนซ์เอง** เลือกจากหน้ารายชื่อฟรีแลนซ์ กรองตามทักษะและงานที่เคยทำ แล้วกด "เชิญมาดูงานนี้"
- **แนะนำฟรีแลนซ์ที่ทักษะตรง** จับคู่ทักษะของงานกับโปรไฟล์ แสดงให้ผู้จ้างเห็น และแจ้งเตือนฟรีแลนซ์เมื่อมีงานใหม่ตรงทักษะ ฝั่งฟรีแลนซ์มีแนะนำงานใน dashboard อยู่แล้ว
- **บอกผู้จ้างว่าทำไมไม่มีคนสนใจ** ผ่านไป 3 วันยังไม่มีข้อเสนอ ให้เตือนว่างบต่ำไป รายละเอียดสั้นไป deadline สั้นไป หรือขอทักษะเยอะเกิน และแนะนำให้แบ่งงานเป็นงวด (4.6)
- **ประกาศหมดอายุ** ครบ 30 วันปิดประกาศอัตโนมัติ แล้วถามผู้จ้างว่าจะแก้แล้วประกาศใหม่ไหม

## 6. ถ้ามีคนไม่ทำตามขั้นตอน

เรื่อง "ไม่ยอมกดปุ่ม" contract รับมือได้เกือบหมดแล้ว ช่องที่เหลือส่วนใหญ่วนกลับมาที่คำถามเดียว คือถ้าคนตัดสินไม่ตัดสินจะเกิดอะไรขึ้น (D1 และ D2 ในข้อ 11)

### เรื่องที่ contract จัดการได้แล้ว

- **ผู้จ้างฝากแล้วเปลี่ยนใจก่อนฟรีแลนซ์รับงาน** ได้เงินคืนเต็มทันที
- **ฟรีแลนซ์ไม่ตอบรับงาน** ผู้จ้างยกเลิกได้ทุกเมื่อ แพลตฟอร์มควรแสดงอัตราการตอบรับงานไว้ในโปรไฟล์
- **ฟรีแลนซ์รับงานแล้วหายไป** ผู้จ้างขอเงินคืนเต็มได้หลัง deadline ถ้าไม่อยากรอก็เปิดข้อพิพาทก่อนได้ ฟรีแลนซ์โดน strike 1 ครั้ง
- **ผู้จ้างเงียบตอนตรวจงาน** ฟรีแลนซ์เบิกเงินเองได้หลัง 7 วัน ข้อเสียคือผู้จ้างที่พลาดการแจ้งเตือนจะจ่ายให้งานที่ไม่ได้ดู แพลตฟอร์มจึงต้องเตือนก่อนหมดเวลา 72 และ 24 ชั่วโมง
- **ผู้จ้างขอแก้ไม่จบ** contract จำกัดไว้ที่ 2 ครั้ง (จะเปลี่ยนเป็นตั้งต่องานตาม 4.3)
- **ผู้รับเงินเป็น contract ที่ไม่ยอมรับ ETH** เงินถูกเก็บเป็นยอดค้างให้มาเบิกเองทีหลัง

### เรื่องที่ยังมีช่องโหว่

- **ผู้รับเงินเป็น contract ที่ตอบกลับด้วยข้อมูลขนาดใหญ่มาก (returndata bomb)** ทำให้การแบ่งเงินในข้อพิพาทและการแบ่งครึ่งตอนหมดเวลาล้มเหลวทุกครั้ง เงินจึงค้างได้ตลอดไป ยืนยันด้วย PoC แล้ว วิธีแก้คือให้ `_send` ไม่ copy ข้อมูลที่ตอบกลับมา แก้แล้ว และมีเทสต์กันไว้
- **ผู้จ้างฝากยอดเงินหรือ deadline ไม่ตรงกับที่ตกลง** แก้แล้ว contract เช็กให้ตอนรับงาน (4.5)
- **ฟรีแลนซ์ไม่ส่งงานแก้** ผู้จ้างต้องเปิดข้อพิพาท ถ้าคนตัดสินเงียบ ฟรีแลนซ์ได้ไปครึ่งหนึ่งทั้งที่ไม่ได้ทำ
- **ผู้จ้างขอแก้ของที่อยู่นอกข้อตกลง** contract แยกไม่ออก คนตัดสินต้องดูตามข้อ 4.3 ฟรีแลนซ์เปิดข้อพิพาทเองได้ก่อนถึง deadline ใหม่
- **เปิดข้อพิพาทแบบไม่มีเหตุผล** ไม่ว่าฝ่ายไหนทำ ถ้าคนตัดสินเงียบ คนเปิดก็ได้กำไร แก้ด้วยการทำให้คนตัดสินเงียบได้ยาก (D2) และให้ strike กับคนที่แพ้ชัดเจน
- **คนตัดสินเงียบ** ตอนนี้แบ่งครึ่งเมื่อครบ 14 วัน ตกลงแล้วว่าจะเพิ่ม wallet สำรองของทีมให้ตัดสินแทนได้หลังวันที่ 7 และทำหน้าจอนับถอยหลังให้คนตัดสิน
- **hash ของงานไม่ตรงกับไฟล์ที่ส่งจริง** contract ไม่รู้ คนตัดสินต้องถือว่ายังไม่ได้ส่งงาน หน้าเว็บควร hash ไฟล์ให้อัตโนมัติและเช็กตอนเปิดไฟล์
- **ทั้งสองฝ่ายอยากตกลงกันเองระหว่างข้อพิพาท** ยอมแพ้ได้แล้ว ส่วนการตกลงแบ่งเงินกันเองยังไม่ได้ทำ (8.5)
- **เจ้าของแพลตฟอร์มเปลี่ยนคนตัดสินหลังฝากเงิน** ทำได้ ฟรีแลนซ์อาจรับงานตอนที่คนตัดสินเป็นคนหนึ่ง แต่พอมีเรื่องกลับเจออีกคน ตกลงแล้วว่าจะล็อกคนตัดสินตั้งแต่ตอนฝาก (D4)

## 7. ถ้างานมีปัญหา หรือมีเรื่องนอก chain

contract มองไม่เห็นเนื้องาน เรื่องในข้อนี้จึงต้องพึ่งคนตัดสิน แพลตฟอร์ม หรือ ToS ตัวเลขเปอร์เซ็นต์ที่เห็นคือส่วนที่ฟรีแลนซ์ควรได้

### เรื่องที่คนตัดสินดูแล

- **งานไม่ครบ หรือฟีเจอร์ใช้ไม่ได้** คนตัดสินไล่ดูรายการตรวจรับทีละข้อ แล้วแบ่งเงินตามระดับใน 8.3 ความไม่ชอบที่ไม่อยู่ในรายการไม่นับ
- **ผู้จ้างขอเกินข้อตกลงแล้วอ้างว่างานไม่ครบ** ตัดสินจากรายการเดิมเท่านั้น ถ้าทำซ้ำจะโดน strike
- **ผู้จ้างเอางานไปใช้แล้วเปิดข้อพิพาทเพื่อไม่จ่าย** ฟรีแลนซ์ได้อย่างน้อย 70% และกันได้ตั้งแต่ต้นด้วยการให้ผู้จ้างดูแค่ตัวทดลองก่อนจ่าย (ข้อ 10)
- **ส่งงานช้า** contract ไม่รับงานหลัง deadline อยู่แล้ว ถ้าฟรีแลนซ์ส่งงานนอกระบบแล้วผู้จ้างเอาไปใช้ ก็จ่ายตามระดับใน 8.3 ข้อเสนอคือให้ผู้จ้างขยาย deadline ให้เองได้
- **ฟรีแลนซ์ทิ้งงานกลางทาง** ถ้ายังไม่เคยส่งงาน ผู้จ้างเปิดข้อพิพาทได้เลย หรือรอถึง deadline แล้วขอคืนเต็ม ถ้าส่งงานไม่ครบไว้แล้วหาย ผู้จ้างเปิดข้อพิพาท คนตัดสินจ่ายตามที่ทำจริง ส่วนใหญ่อยู่ระดับ 1 คือ 10–30% ทั้งสองกรณีฟรีแลนซ์โดน strike และหน้าเว็บมีปุ่ม "จ้างคนใหม่ทำต่อ" ที่ยกข้อที่ยังไม่ผ่านไปเป็นประกาศงานใหม่ ถ้าแบ่งงวด งวดที่จ่ายไปแล้วไม่ถูกดึงคืน (4.6)
- **ลอกงาน ละเมิดลิขสิทธิ์ หรือใช้ AI ทั้งที่ตกลงกันว่าห้าม** ฟรีแลนซ์ได้ 0% และโดนแบน ToS ต้องให้ฟรีแลนซ์รับรองว่าเป็นเจ้าของงาน
- **ไฟล์มีมัลแวร์** ได้ 0% และโดนแบน แพลตฟอร์มควรสแกนไฟล์ก่อน

### เรื่องที่แพลตฟอร์มหรือกฎหมายดูแล

- **ทำข้อมูลลับรั่ว** ไม่เกี่ยวกับ escrow เพราะความเสียหายอาจมากกว่าค่าจ้าง ใช้การแบนและช่องทางกฎหมาย
- **ชวนไปจ่ายนอกแพลตฟอร์ม** โดนแบน และงานที่ทำนอกระบบไม่ได้รับการคุ้มครอง
- **คุกคามหรือพฤติกรรมไม่เหมาะสม** ระงับบัญชี ถ้ากระทบงาน คนตัดสินนำมาประกอบได้
- **บัญชีปลอม ปั่นรีวิว หรือจ้างตัวเอง** contract กันได้แค่กรณีผู้จ้างกับฟรีแลนซ์เป็น address เดียวกัน ที่เหลือแพลตฟอร์มต้องตรวจ wallet ซ้ำแล้วแบนเอง
- **ติดต่อไม่ได้แต่ยังไม่ถึง deadline** ไม่มีผลอะไรบน chain จนกว่าจะถึง deadline แพลตฟอร์มทำได้แค่แจ้งเตือน

ระบบ strike ที่เสนอ: ครั้งแรกเตือน ครั้งที่สองระงับบัญชี 30 วัน ครั้งที่สามแบน นับเฉพาะคดีที่คนตัดสินระบุว่าผิดชัดเจน การแบ่งครึ่งเพราะหมดเวลาไม่นับ

## 8. เวลามีข้อพิพาท

ข้อพิพาททุกเรื่องต้องจบภายใน 14 วัน เจ้าของแพลตฟอร์มซึ่งเป็นคนตัดสินมีเวลา 7 วันแรก ถ้าไม่ตัดสิน wallet สำรองของทีมตัดสินแทนได้ในวันที่ 7 ถึง 14 ระหว่างนั้นคู่กรณียอมแพ้ได้ตลอด ส่วนการตกลงแบ่งเงินกันเองยังเป็นข้อเสนอ

### 8.1 ลำดับเวลา

1. **วันที่ 0** ฝ่ายหนึ่งเปิดข้อพิพาท เหตุผลที่ใส่บน chain ให้สั้นและไม่มีข้อมูลส่วนตัว รายละเอียดไปยื่นบนแพลตฟอร์ม
2. **วันที่ 0–3** ทั้งสองฝ่ายยื่นหลักฐาน แพลตฟอร์ม hash ทุกชิ้นตอนรับ
3. **วันที่ 3–7** คนตัดสินดูหลักฐาน ตัดสินตาม 8.3 แล้วเรียก `resolveDispute`
4. **วันที่ 7–14** ถ้าเจ้าของยังเงียบ wallet สำรองของทีมตัดสินแทนได้
5. **หลังวันที่ 14** ใครก็ได้สั่ง `settleExpiredDispute` ผลคือแบ่งครึ่งและไม่เก็บค่าธรรมเนียม (D2, D3)

### 8.2 หลักฐานแบบไหนใช้ได้

หลักฐานที่ใช้ได้เต็มที่คือของที่พิสูจน์ได้ว่าไม่ถูกแก้ทีหลัง ได้แก่ ข้อตกลงที่ hash ตรงกับ termsHash บน chain ไฟล์งานที่ hash ตรงกับ workHash ตอนส่งงาน แชตบนแพลตฟอร์มซึ่งแก้ย้อนหลังไม่ได้ และหลักฐานที่ยื่นในวันที่ 0–3 ซึ่งแพลตฟอร์มบันทึก hash กับเวลาไว้

แชตนอกแพลตฟอร์ม หรือไฟล์ที่ hash ไม่ตรง ใช้ได้แค่ประกอบ ให้น้ำหนักน้อย

### 8.3 แบ่งเงินยังไง

คนตัดสินไล่ดูรายการตรวจรับ (4.2) ทีละข้อ แล้วเลือกระดับจากตารางนี้ ตัวเลขเป็นของแพลตฟอร์มที่ประกาศไว้ในหน้าช่วยเหลือ ไม่มีใครต้องคิดเอง ตอนส่งเข้า `resolveDispute` ให้แปลงเป็น bps (1% = 100 bps)

| ระดับ | สภาพงาน | ฟรีแลนซ์ได้ |
| --- | --- | --- |
| 0 | ไม่ส่ง รันไม่ขึ้น ลอกงาน มีมัลแวร์ หรือ hash ไม่ตรง | 0% |
| 1 | รันได้ แต่ข้อ "ต้องมี" ผ่านไม่ถึงครึ่ง | 10–30% |
| 2 | ข้อ "ต้องมี" ผ่านครึ่งหนึ่งขึ้นไป แต่ไม่ครบ | 40–60% |
| 3 | ข้อ "ต้องมี" ผ่านครบ แต่ข้อ "เสริม" ยังขาด | 70–90% |
| 4 | ผ่านครบทุกข้อ ผู้จ้างแค่ไม่ชอบหรือขอของนอกรายการ | 100% |

- ในแต่ละระดับ ให้ขยับตามสัดส่วนข้อที่ผ่าน เช่น อยู่ระดับ 3 และข้อเสริมผ่าน 1 ใน 2 ข้อ ก็ให้ 80%
- ถ้าผู้จ้างเอางานไปใช้จริงแล้ว ให้อย่างน้อย 70% เพราะใช้งานได้แปลว่าข้อหลักทำงาน
- ของที่ขอนอกรายการไม่นำมาคิด
- ถ้าหลักฐานไม่พอทั้งสองฝ่าย ให้ 50%
- คนตัดสินต้องรันโค้ดเป็น เพราะเรื่อง source code กับวิธีติดตั้ง ผู้จ้างตรวจเองไม่ได้ เจ้าของและคนถือ wallet สำรองจึงต้องเป็น dev
- คนตัดสินเขียนเหตุผลอ้างรายการทีละข้อ แล้วส่งให้ทั้งสองฝ่ายทันที

### 8.4 บันทึกคำตัดสิน (เสนอ)

เพิ่มพารามิเตอร์เป็น `resolveDispute(escrowId, freelancerBps, rulingHash)` เพื่อเก็บ hash ของเอกสารคำตัดสินไว้ใน event ใครก็เช็กได้ว่าเอกสารไม่ถูกแก้ทีหลัง และใช้ตรวจการทำงานของคนตัดสินย้อนหลังได้

### 8.5 ยอมแพ้หรือตกลงกันเองระหว่างข้อพิพาท

ระหว่างข้อพิพาท ผู้จ้างกดจ่ายเต็มได้ และฟรีแลนซ์กดคืนเงินเต็มได้ (ทำแล้ว) ไม่มีความเสี่ยง เพราะคนที่เสียเปรียบคือคนกดเอง (หลักข้อ 3)

อีกทางคือเพิ่ม `proposeSettlement(escrowId, bps)` ให้ทั้งสองฝ่ายเสนอสัดส่วนแบ่งเงิน ถ้าเสนอตรงกันก็จบทันทีโดยไม่ต้องรอคนตัดสิน คดีที่ตกลงกันได้จะไม่ไปค้างที่คนตัดสิน งานของคนตัดสินก็น้อยลง และโอกาสที่จะหมดเวลาก็น้อยลงด้วย

ถ้าจบด้วยการยอมแพ้หรือตกลงกันเอง คิดค่าธรรมเนียมแบบปกติตามส่วนที่ฟรีแลนซ์ได้ ไม่ใช่แบบไม่เก็บตาม D3 ไม่อย่างนั้นผู้จ้างจะเปิดข้อพิพาทแล้วยอมจ่ายทันทีเพื่อเลี่ยง 5%

## 9. เงินและค่าธรรมเนียม

ค่าจ้างถูกล็อกเป็น ETH ตั้งแต่วันที่ฝาก ตัวเลขเงินบาทที่เห็นเป็นแค่ค่าอ้างอิง ถ้าราคา ETH ขึ้นหรือลงหลังฝาก ยอดที่จ่ายก็ยังเป็น ETH เท่าเดิม ข้อนี้ควรเขียนไว้ใน ToS (เสนอ)

เรื่องที่โค้ดทำอยู่แล้ว

- จ่ายเป็น ETH บน Sepolia
- ค่าธรรมเนียม 5% บวกเพิ่มจากค่าจ้าง ผู้จ้างจ่ายรวม 105%
- ค่าธรรมเนียมใช้อัตราตอนฝาก ถ้าเจ้าของแพลตฟอร์มเปลี่ยนทีหลัง งานเดิมไม่กระทบ
- ถ้าคืนเงินเต็ม ผู้จ้างได้คืน 105% รวมค่าธรรมเนียม
- ถ้าแบ่งเงินในข้อพิพาท ตอนนี้ค่าธรรมเนียมคิดตามสัดส่วนที่ฟรีแลนซ์ได้ ตกลงแล้วว่าจะเปลี่ยนเป็นไม่เก็บเลยเมื่อจบด้วยคำตัดสินหรือหมดเวลา (D3)
- เศษ wei จากการหารปัดให้ผู้จ้าง
- ค่า gas แต่ละฝ่ายจ่ายเอง
- ผู้รับที่รับ ETH ไม่ได้ เงินจะถูกเก็บเป็นยอดค้างให้มาเบิกเอง
- หน้าเว็บแปลงเป็นบาทด้วยอัตราคงที่ `VITE_THB_PER_ETH` และแสดงคู่กับยอด ETH ทุกหน้า

ตัวอย่างเมื่อค่าจ้างคือ 1 ETH (ผู้จ้างฝาก 1.05 ETH)

| จบแบบไหน | ฟรีแลนซ์ได้ (ETH) | แพลตฟอร์มได้ (ETH) | ผู้จ้างได้คืน (ETH) |
| --- | --- | --- | --- |
| จ่ายปกติ | 1 | 0.05 | 0 |
| คืนเงินเต็ม | 0 | 0 | 1.05 |
| คนตัดสินให้ฟรีแลนซ์ 60% (กติกาใหม่ตาม D3) | 0.6 | 0 | 0.45 |

แถวสุดท้ายใช้กติกาใหม่ ตอนนี้โค้ดยังให้แพลตฟอร์ม 0.03 และคืนผู้จ้าง 0.42

## 10. ส่งไฟล์งานและลิขสิทธิ์

ปัญหา "ได้งานแล้วไม่จ่าย" แก้ได้ด้วยการส่งงานเป็นสองขั้น ตอนส่งงาน ฟรีแลนซ์ล็อก hash ของไฟล์จริงไว้บน chain ก่อน แต่ให้ผู้จ้างลองใช้แค่ตัวทดลอง ส่วน source code จริงส่งให้หลังจ่ายเงินแล้ว

1. ฟรีแลนซ์เตรียมไฟล์จริงให้ครบ แล้วคำนวณ workHash จากรายชื่อไฟล์พร้อม hash ของแต่ละไฟล์
2. เรียก `submitWork(escrowId, workHash)` เพื่อล็อก hash ไว้บน chain แก้ทีหลังไม่ได้
3. ผู้จ้างตรวจงานจากลิงก์ทดลองใช้ ยังไม่ได้ source code
4. พอจ่ายแล้ว ฟรีแลนซ์ส่งไฟล์จริง และหน้าเว็บเช็กให้ว่า hash ตรงกับ workHash
5. ถ้ามีข้อพิพาท ฟรีแลนซ์ส่งไฟล์จริงให้คนตัดสินตรวจ ไฟล์ที่ hash ไม่ตรงถือว่าไม่ได้ส่ง

ตอนนี้ workHash อยู่แค่ใน event ข้อเสนอคือเก็บค่าล่าสุดไว้ใน struct ด้วย จะได้อ่านจาก `getEscrow` ได้ตรง ๆ

เรื่องลิขสิทธิ์ ซึ่งต้องเขียนไว้ใน ToS

- ก่อนจ่ายครบ ผู้จ้างมีสิทธิ์แค่ทดลองใช้ ห้ามเอาไปใช้จริง
- พอจ่ายครบ ไม่ว่าจะกดจ่ายเองหรือคนตัดสินให้ฟรีแลนซ์ 100% ลิขสิทธิ์โอนตามที่เขียนไว้ในฟิลด์ `ip`
- ถ้าคนตัดสินแบ่งเงิน ต้องระบุด้วยว่าผู้จ้างได้สิทธิ์ในส่วนไหน ค่าตั้งต้นคือเฉพาะส่วนที่ผ่านรายการตรวจรับ (ยังไม่ได้ตกลง)
- ฟรีแลนซ์เอางานไปลงผลงานได้ ยกเว้นข้อตกลงระบุว่าเป็นงานลับ
- ถ้าจ่ายแล้วแต่ไฟล์จริงที่ได้ไม่ตรง hash เงินออกจาก escrow ไปแล้ว contract ช่วยไม่ได้ เหลือแค่การแบนและ ToS

## 11. เรื่องที่ต้องตัดสินใจ

ตัดสินใจครบทุกข้อแล้ว: เจ้าของแพลตฟอร์มตัดสินเอง มี wallet สำรองของทีมตัดสินแทนหลังวันที่ 7 ถ้าเงียบทั้งคู่ครบ 14 วันค่อยแบ่งครึ่ง ไม่เก็บค่าธรรมเนียมจากงานที่จบด้วยคำตัดสิน และล็อกคนตัดสินตั้งแต่ตอนฝาก การเทียบทางเลือกด้านล่างเก็บไว้เป็นเหตุผลประกอบ

| ได้เงินจากผลตัดสินไหม | ได้ เพราะค่าธรรมเนียมคิดตามส่วนที่ฟรีแลนซ์ได้ ยิ่งให้ฟรีแลนซ์มากยิ่งได้มาก | ไม่ได้ ถ้าแอดมินไม่ใช่คนรับค่าธรรมเนียม |
| อคติทางธุรกิจ | อาจเอียงเข้าหาลูกค้ารายใหญ่ | น้อยกว่า ถ้ามีแนวตัดสินชัดและตรวจย้อนหลังได้ |
| โอกาสรับสินบน | ต่ำกว่า เพราะเสี่ยงเสียชื่อทั้งแพลตฟอร์ม | สูงกว่า ลดได้ด้วยการบันทึก hash คำตัดสินและสุ่มตรวจ |
| ถ้า key รั่ว | key เดียวคุมทั้งการตั้งค่าและการตัดสิน | เสียหายแค่บทบาทเดียว |
| ความเร็ว | เจ้าของมีงานเยอะ มีโอกาสหมดเวลามากกว่า | มีคนดูแลโดยตรง |
| ถ้าคนตัดสินเงียบ | ไม่มีตัวสำรอง หมดเวลาแล้วแบ่งครึ่งเลย | เจ้าของตัดสินแทนได้ |
| ต้องทำอะไรเพิ่มสำหรับ demo | ไม่ต้อง สคริปต์ deploy ตั้งแบบนี้อยู่แล้ว | เพิ่ม wallet อีก 1 อัน และแก้ contract นิดหน่อยให้มีตัวสำรอง |
| ผู้ใช้มองยังไง | เจ้าของเว็บตัดสินเรื่องที่ตัวเองได้เงิน | แยกหน้าที่ชัดเจน |

**ตัดสินใจ: A เจ้าของตัดสินเอง** ข้อเสียเรื่องผลประโยชน์ทับซ้อนแก้ด้วย D3 คือไม่เก็บค่าธรรมเนียมจากงานที่จบด้วยคำตัดสิน ส่วนข้อเสียเรื่องไม่มีตัวสำรองแก้ด้วย wallet สำรองของทีม (D2) เจ้าของและคนถือ wallet สำรองต้องรันโค้ดเป็น (8.3)

### D2 ถ้าไม่มีใครตัดสินเลย เงินควรไปทางไหน

contract ไม่รู้ว่าใครถูก สิ่งที่เลือกได้คือถ้าทุกคนเงียบ จะให้ใครได้ประโยชน์ มีสามทางให้เลือก

- **แบ่งครึ่งเสมอ** ซึ่งคือสิ่งที่โค้ดทำอยู่ตอนนี้
- **ดูว่าเคยส่งงานไหม** ถ้ายังไม่เคยส่ง ผู้จ้างได้คืนเต็ม ถ้าเคยส่งแล้วก็แบ่งครึ่ง
- **คนเปิดข้อพิพาทต้องพิสูจน์** ถ้าไม่มีใครตัดสิน ฝ่ายที่ไม่ได้เปิดชนะ

ตารางนี้ดูว่า ถ้าคนตัดสินเงียบ คนที่ผิดจะได้เงินเกินกว่าที่ควรได้กี่เปอร์เซ็นต์ของค่าจ้าง ตัวเลขติดลบแปลว่าคนผิดกลับเสียเปรียบ

| สถานการณ์ | ใครผิด | ฟรีแลนซ์ควรได้ | แบ่งครึ่ง | ดูการส่งงาน | คนเปิดต้องพิสูจน์ |
| --- | --- | --- | --- | --- | --- |
| ผู้จ้างได้งานดีแล้วเปิดข้อพิพาทเพื่อไม่จ่าย | ผู้จ้าง | 100% | +50 | +50 | 0 |
| ฟรีแลนซ์ส่งงานขยะ ผู้จ้างเปิดข้อพิพาทโดยสุจริต | ฟรีแลนซ์ | 0% | +50 | +50 | +100 |
| ฟรีแลนซ์ไม่ทำงาน แต่ชิงเปิดข้อพิพาทก่อน deadline | ฟรีแลนซ์ | 0% | +50 | 0 | 0 |
| ผู้จ้างเลิกกลางทางทั้งที่ฟรีแลนซ์ทำไปครึ่งหนึ่งแล้ว | ผู้จ้าง | ประมาณ 50% | 0 | +50 | −50 |
| ฟรีแลนซ์หายไปหลังโดนขอแก้ ผู้จ้างเปิดข้อพิพาท | ฟรีแลนซ์ | ประมาณ 0% | +50 | +50 | +100 |
| **คนผิดได้มากสุด** |  |  | **50** | **50** | **100** |

อ่านจากตารางได้ว่า

- **แบ่งครึ่งคือทางที่คนโกงได้น้อยที่สุดแล้ว** ถ้าผลตั้งต้นให้ฟรีแลนซ์ x% ผู้จ้างที่โกงจะได้ 100 − x ส่วนฟรีแลนซ์ที่โกงจะได้ x จุดที่ทำให้ฝ่ายที่ได้มากกว่าได้น้อยที่สุดคือ x = 50 เหตุผลนี้แม่นกว่าที่เอกสาร v0.2 เขียนว่า "ไม่มีใครได้ประโยชน์จากความเงียบ"
- **"คนเปิดต้องพิสูจน์" ฟังดูยุติธรรม แต่ใช้กับระบบนี้ไม่ได้** เพราะคนที่ต้องเปิดข้อพิพาทแทบทุกครั้งคือผู้จ้าง ผลจริงจึงกลายเป็น "คนตัดสินเงียบเมื่อไหร่ ฟรีแลนซ์ชนะ" ผู้จ้างที่สุจริตเสียเงินทั้งหมด
- **"ดูการส่งงาน" ปิดช่องฟรีแลนซ์ที่ไม่ทำงานได้** แต่คนโกงแค่เปลี่ยนไปส่งงานขยะก่อนก็ยังได้ 50% เท่าเดิม แถมเปิดช่องให้ผู้จ้างที่เลิกกลางทางได้เปรียบ
- **ไม่ว่าเลือกแบบไหน ก็ไม่ได้แก้ที่ต้นเหตุ** ต้นเหตุคือคนตัดสินเงียบ ทางแก้จริงคือทำให้คนตัดสินเงียบได้ยาก

**ตัดสินใจ: คงแบ่งครึ่งไว้เป็นทางสุดท้าย และเพิ่ม wallet สำรองของทีมที่ตัดสินแทนได้หลังวันที่ 7** ไม่ใช้แบบ "ดูการส่งงาน" ส่วนที่เหลือทำตามเดิม คือให้ยอมแพ้หรือตกลงกันเองได้ (8.5) ใช้ strike กับคนที่แพ้ชัดเจนซ้ำ ๆ และแก้คำอธิบายในเอกสาร v0.2 ให้ใช้เหตุผลข้างบน

### D3 ค่าธรรมเนียมตอนมีข้อพิพาท

ตอนนี้ค่าธรรมเนียมคิดตามส่วนที่ฟรีแลนซ์ได้ ยิ่งตัดสินให้ฟรีแลนซ์มาก คนรับค่าธรรมเนียมก็ยิ่งได้มาก มีสามทางให้เลือก

- **ก. คงไว้แบบเดิม** เก็บเฉพาะส่วนที่จ่ายฟรีแลนซ์จริง ข้อเสียคือถ้าคนตัดสินเป็นคนรับค่าธรรมเนียมด้วย ก็มีเหตุให้เอียง
- **ข. เก็บเต็มทุกคดีที่มีการตัดสิน** แพลตฟอร์มได้เท่าเดิมไม่ว่าผลจะออกมายังไง ข้อเสียคือผู้จ้างเสียค่าธรรมเนียมเต็มแม้งานล้ม
- **ค. ไม่เก็บเลยถ้ามีข้อพิพาท** คนตัดสินไม่ได้อะไรจากผล ข้อเสียคือแพลตฟอร์มตัดสินให้ฟรี

**ตัดสินใจ: ค ไม่เก็บค่าธรรมเนียมเมื่องานจบด้วยคำตัดสินหรือหมดเวลา** ผู้จ้างได้ค่าธรรมเนียมคืนเต็ม ส่วนการยอมแพ้หรือตกลงกันเองระหว่างข้อพิพาทยังคิดค่าธรรมเนียมแบบปกติ ไม่อย่างนั้นผู้จ้างจะเปิดข้อพิพาทแล้วยอมจ่ายทันทีเพื่อเลี่ยง 5%

ข้อเสียที่ยังเหลือ: ผู้จ้างอาจเปิดข้อพิพาททั้งที่งานใช้ได้ เพื่อให้เจ้าของตัดสินแล้วไม่ต้องจ่าย 5% แลกกับเงินที่ถูกล็อกนานขึ้น กันด้วย strike เมื่อผู้จ้างแพ้ชัดเจน

### D4 ควรล็อกคนตัดสินไว้ตอนไหน

ตอนนี้ contract บันทึกว่าใครเป็นคนตัดสินตอนเปิดข้อพิพาท แปลว่าเจ้าของแพลตฟอร์มเปลี่ยนคนตัดสินได้จนถึงวันที่มีเรื่อง ฟรีแลนซ์อาจรับงานตอนที่คนตัดสินเป็นคนหนึ่ง แต่พอมีเรื่องกลับเจออีกคน

**ตัดสินใจ: ล็อกตั้งแต่ตอนฝากเงิน** ทั้ง address คนตัดสินและ wallet สำรอง ทั้งสองฝ่ายเห็นก่อนเริ่มงาน ถ้า key ของเจ้าของหาย wallet สำรองยังตัดสินงานที่ค้างอยู่ได้

### D5 ให้วางมัดจำตอนเปิดข้อพิพาทไหม

แนวคิดคือคนเปิดข้อพิพาทต้องวางเงินเพิ่ม เช่น 5% ของค่าจ้าง ถ้าแพ้ชัดเจนก็เสียมัดจำให้อีกฝ่าย ถ้าหมดเวลาก็ได้คืน ข้อดีคือการเปิดข้อพิพาทมั่ว ๆ มีต้นทุน แม้คนตัดสินจะตอบเร็ว ข้อเสียคือต้องนิยามคำว่า "แพ้" ตอนแบ่งเงิน คนสุจริตที่เงินน้อยอาจไม่กล้าเปิด และโค้ดซับซ้อนขึ้นมาก

**ตัดสินใจ: ไม่ทำใน demo** เขียนไว้เป็นงานต่อยอด

## 12. กรณีแปลก ๆ ที่ต้องคิดเผื่อ

ถ้าใครทำ key หาย ระบบยังไปต่อได้เกือบทุกกรณี เพราะทุกจังหวะมีทางออกเมื่อหมดเวลา ข้อยกเว้นเดียวคือการจ่ายเงินไปที่ address ที่เจ้าของทำ key หายไปแล้ว

- **ผู้จ้างทำ key หาย** ฟรีแลนซ์ยังส่งงานได้ แล้วเบิกเงินเองหลังหมดเวลาตรวจ
- **ฟรีแลนซ์ทำ key หายก่อนส่งงาน** ผู้จ้างขอเงินคืนได้หลัง deadline
- **ฟรีแลนซ์ทำ key หายหลังส่งงาน** ผู้จ้างเปิดข้อพิพาทได้ แต่ถ้ากดจ่าย เงินจะไปที่ address ที่หายไปแล้ว หน้าเว็บต้องเตือนเรื่องนี้
- **เจ้าของซึ่งเป็นคนตัดสินทำ key หาย** wallet สำรองตัดสินข้อพิพาทที่ค้างอยู่แทนได้ แต่เปลี่ยนการตั้งค่าไม่ได้อีก escrow ที่มีอยู่ไม่กระทบ
- **wallet สำรองทำ key หาย** ไม่กระทบอะไร ตราบใดที่เจ้าของยังตัดสินทันเวลา
- **ใส่ address ฟรีแลนซ์ผิด** ยกเลิกแล้วได้เงินคืนเต็ม ถ้าฝั่งนั้นยังไม่รับงาน
- **อยากเปลี่ยน wallet กลางงาน** ตอนนี้ทำไม่ได้ address ผูกตายตัว อนาคตอาจให้เปลี่ยนได้ถ้าทั้งสองฝ่ายยินยอม
- **ผู้จ้างตั้ง deadline สั้นผิดปกติ** หน้าเว็บบังคับขั้นต่ำ 7 วันแล้ว แต่ contract ยังไม่มีขั้นต่ำ ฟรีแลนซ์ต้องเห็นก่อนรับงาน (4.5)
- **เจอบั๊กหลัง deploy** ไม่มีการอัปเกรดหรือหยุดระบบ งานใหม่ไปใช้ contract ตัวใหม่ งานเก่าจบบนตัวเดิม ตั้งใจออกแบบแบบนี้ เพราะถ้าใช้ proxy ที่อัปเกรดได้ เจ้าของจะเปลี่ยนกติกาของงานที่กำลังเดินอยู่ได้ ซึ่งขัดหลักข้อ 5
- **มีคนส่ง ETH เข้า contract ตรง ๆ** ไม่กระทบ escrow ไหน เพราะ contract ไม่ได้ใช้ยอดคงเหลือรวมมาคำนวณ
- **chain reorg** backend ต้องรอหลาย block ก่อนถือว่าธุรกรรมสำเร็จ

## 13. ความเป็นส่วนตัวและอำนาจของเจ้าของแพลตฟอร์ม

ทุกอย่างที่อยู่บน chain เป็นสาธารณะและลบไม่ได้ ส่วนเจ้าของแพลตฟอร์มมีอำนาจแค่ตั้งค่าสำหรับงานในอนาคต แตะเงินหรือแก้ escrow ที่มีอยู่ไม่ได้

### 13.1 อะไรบ้างที่คนอื่นเห็น

ใครก็เห็น address ของผู้จ้าง ฟรีแลนซ์ และคนตัดสิน รวมถึงยอดเงิน ค่าธรรมเนียม deadline และเวลาของทุกขั้น termsHash กับ workHash เป็นแค่ hash จึงไม่เผยเนื้อหา แต่ข้อความ `reason` ตอนขอแก้และตอนเปิดข้อพิพาทเป็นข้อความจริงที่ทุกคนอ่านได้

เพราะฉะนั้น

- หน้าเว็บต้องเตือนและจำกัดความยาวของ reason ห้ามใส่ชื่อ เบอร์โทร อีเมล หรือรายละเอียดงานลับ
- ToS ต้องบอกผู้ใช้ว่าธุรกรรมบน blockchain ลบไม่ได้
- ยังไม่ได้ตัดสินใจว่าจะเปลี่ยน reason เป็น hash แล้วเก็บข้อความจริงไว้บนแพลตฟอร์มไหม ข้อดีคือเป็นส่วนตัวและเสีย gas น้อยลง ข้อเสียคือคนนอกอ่านเหตุผลจาก chain ไม่ได้

### 13.2 เจ้าของแพลตฟอร์มทำอะไรได้บ้าง

เจ้าของทำได้ 4 อย่าง คือ ตั้งค่าธรรมเนียมไม่เกิน 10% สำหรับงานใหม่ เปลี่ยนคนตัดสินและ wallet สำรองสำหรับงานที่ฝากใหม่ (งานเดิมใช้คนที่ล็อกไว้ตอนฝาก) เปลี่ยน wallet รับค่าธรรมเนียม (มีผลกับการจ่ายครั้งถัดไปของทุกงาน) และโอนหรือสละสิทธิ์ความเป็นเจ้าของ

สิ่งที่ทำไม่ได้คือ ย้ายหรือถอนเงินใน escrow แก้สถานะ ยอดเงิน หรือ deadline ของงาน เปลี่ยนเวลาตรวจงาน เวลาแก้งาน จำนวนรอบแก้ หรือเวลาหมดของข้อพิพาท (ค่าพวกนี้ตั้งตายตัวตอน deploy) และหยุดระบบ (ไม่มีปุ่ม pause)

ข้อเสนอ

- ใช้ `Ownable2Step` กันการโอนสิทธิ์ไปผิด address และปิด `renounceOwnership` กันพลาดสละสิทธิ์แล้วตั้งค่าอะไรไม่ได้อีก
- ต้องเช็ก `ConflictOfInterest` กับ wallet สำรองด้วย ทั้งเจ้าของและ wallet สำรองต้องไม่ใช่ผู้จ้างหรือฟรีแลนซ์ของงานนั้น
- แจ้งผู้ใช้ทุกครั้งที่มีการเปลี่ยนค่าธรรมเนียม คนตัดสิน หรือ wallet รับค่าธรรมเนียม

สิ่งที่ทำไปแล้วและสิ่งที่ต้องทำต่อ

- เพิ่มเทสต์แล้ว 7 ข้อ: returndata bomb 2 ข้อ (ล้มกับโค้ดเดิม ผ่านกับโค้ดใหม่) `TermsMismatch` 1 ข้อ และยอมแพ้ระหว่างข้อพิพาท 3 ข้อ เทสต์เดิมที่ล็อกว่า "ผู้จ้างกดจ่ายระหว่างข้อพิพาทไม่ได้" แก้ตามกติกาใหม่แล้ว
- ABI ของ `acceptEscrow` เปลี่ยน export ไปหน้าเว็บแล้ว แต่ contract บน Sepolia ยังเป็นตัวเก่า ต้อง deploy ใหม่ก่อนหน้าเว็บจะกดรับงานได้
- ยังต้องเพิ่ม invariant test 4 ข้อ คือ เงินใน contract พอจ่ายเสมอ ไม่มีเงินหายหรือจ่ายซ้ำ งานที่จบแล้วเปลี่ยนสถานะไม่ได้ และเงินไม่ค้างตลอดไป โดยใส่ผู้เล่นที่ตั้งใจโกงไว้ในชุดทดสอบแบบสุ่มด้วย
- แก้เอกสาร v0.2 ข้อ 5b ให้ใช้เหตุผลเรื่องแบ่งครึ่งตาม D2
