# บันทึกงาน Freelink Backend

## 23 พฤศจิกายน 2026 · แนบข้อมูลคู่สัญญาใน job, proposal และ project

### ที่มาของปัญหา

- ลองใช้งานผ่านเบราว์เซอร์จริงเป็นผู้จ้างและฟรีแลนซ์ พบว่าหน้าเว็บแสดง `—` หรือช่องว่างตรงที่ควรมีชื่อและสถิติ: กล่อง "ฟรีแลนซ์/ลูกค้า" และ "เริ่มเมื่อ" ในหน้าโปรเจกต์, บรรทัด `ลูกค้า: —` ในแดชบอร์ดฟรีแลนซ์, ป้าย "งานที่ประกาศ / จ้างสำเร็จ %" ในหน้ารายละเอียดงาน
- สาเหตุเดียวกัน: `job.client`, `proposal.freelancer` ส่งกลับเพียง `{id, name}` และ `ProjectResponse` ไม่มีทั้ง `client`, `freelancer`, `startDate` แต่หน้าเว็บอ่านชื่อ เรตติ้ง จำนวนงานที่เสร็จ ทักษะ ฯลฯ จากฟิลด์เหล่านั้น (`JobDetails.jsx`, `ProjectDetails.jsx`, `CompareProposals.jsx`, `ReviewWork.jsx`, `HiringHistory.jsx`, `ClientDashboard.jsx`) ค่าที่ไม่มีจึงถูกพิมพ์เป็นว่างโดยไม่มี error
- หน้าเปรียบเทียบข้อเสนอที่ผู้จ้างใช้เลือกคนก็ได้รับผลเดียวกัน (เรตติ้ง จำนวนงานที่เสร็จ ทักษะ ตำแหน่งว่าง) จึงแก้ในรอบเดียวกัน สคริปต์ `scripts/flow_trace.py` ตรวจเฉพาะว่า route มีจริง จึงจับเรื่องรูปร่างข้อมูลไม่ได้

### งานที่เสร็จ

- เพิ่ม `ClientCard` และ `FreelancerCard` ใน `schemas.py` (ขยายจาก `PublicProfile` จึงยังมี `id`, `name` เหมือนเดิม) ใช้เป็นชนิดของ `JobResponse.client`, `ProposalResponse.freelancer` และเพิ่ม `ProjectResponse.client`, `ProjectResponse.freelancer`, `ProjectResponse.startDate` (ค่าเดียวกับ `createdAt` เพราะโปรเจกต์เริ่มตอนจ้าง)
- เพิ่ม `client_cards()` และ `freelancer_cards()` ใน `profiles.py` โหลดทั้งรายการด้วย query ชุดเดียวต่อชนิด ไม่ยิงทีละแถว สูตร `jobsPosted`/`hireRate` และ `completedJobs`/`successRate` ใช้ตัวเดียวกับ `GET /clients/{id}` และ `GET /freelancers` (แยก `project_outcomes()` และ `hire_percent()` ออกมาใช้ร่วมกัน พฤติกรรมของ `freelancer_rows` และ `client_view` ไม่เปลี่ยน)
- ต่อเข้า `list_jobs`, `job_details`, `client_jobs`, `proposal_views`, `project_views` และ `GET /admin/overview` ผ่าน `with_clients()` ใน `marketplace.py`
- Card ของฟรีแลนซ์ไม่กรองสถานะบัญชี เพื่อให้ฟรีแลนซ์ที่ถูกระงับหลังยื่นข้อเสนอยังมีชื่อในรายการของผู้จ้าง ส่วนไดเรกทอรีฟรีแลนซ์ยังกรองบัญชีที่ถูกระงับเหมือนเดิม
- ความเป็นส่วนตัว: `GET /jobs/{id}` เปิดให้คนที่ยังไม่ล็อกอินอ่าน ส่วน `GET /clients/{id}` ต้องล็อกอิน card ของลูกค้าจึงมีเฉพาะชื่อ สีอวาตาร์ และสถิติ ไม่มี `bio`, `title`, `location`, อีเมล หน้ารายละเอียดงานที่อ่านฟิลด์เหล่านั้นจึงยังว่างไว้ รอตัดสินใจว่าจะเปิดเผยข้อมูลบริษัทต่อสาธารณะหรือไม่ เรตติ้งและรีวิวยังเป็น 0 จนกว่าจะมีโฟลว์รีวิว
- ไม่มี migration ไม่แก้ React (โค้ดหน้าเว็บอ่านชื่อฟิลด์ถูกอยู่แล้ว) ต้องรีสตาร์ต Uvicorn เพื่อให้หน้าเว็บเห็นการเปลี่ยนแปลง

### ผลการทดสอบ

- ก่อนแก้ ชุดทดสอบ PostgreSQL ผ่าน 13 รายการ หลังแก้ผ่าน 14 รายการ เพิ่ม `test_jobs_proposals_and_projects_carry_the_other_partys_card` ตรวจสถิติลูกค้าบนหน้า public, ชื่อและทักษะของผู้สมัคร (รวมผู้สมัครที่ถูกระงับ), ชื่อทั้งสองฝ่ายและ `startDate` ในโปรเจกต์ทั้งมุมมองผู้จ้างและฟรีแลนซ์ และตรวจว่า `email`, `bio`, `hourlyRate` ไม่หลุดออกมา
- ปิด `with_clients()` ชั่วคราวในหน่วยความจำแล้วรันเทสต์ใหม่ ล้มด้วยค่า `(Acme Studio, None, None, None)` แทนสถิติ แสดงว่าเทสต์จับบั๊กนี้ได้จริง
- เพิ่ม 3 รายการตรวจรูปร่างข้อมูลใน `scripts/flow_trace.py` (สถิติลูกค้าในหน้ารายละเอียดงาน, ข้อมูลผู้สมัคร, ชื่อสองฝ่ายในโปรเจกต์) รันกับ API เดิมบนพอร์ต 8000 ไม่ผ่าน 3 รายการ รันกับ Uvicorn ที่เปิดใหม่ด้วยโค้ดที่แก้บนพอร์ต 8010 (ฐานข้อมูล dev เดียวกัน) ผ่านทั้งหมดรวมขั้นส่งงาน ขอแก้ และอนุมัติ ปิดตัวที่ 8010 แล้ว และลบข้อมูลทดสอบ `flowtest-*` ออกจากฐานข้อมูลพัฒนา
- ยังไม่ได้เปิดดูหน้าเว็บจริงหลังแก้ เพราะ Uvicorn ที่พอร์ต 8000 ยังรันโค้ดเดิม

### ตรวจการไหลของข้อมูลจากฟอร์มถึง backend (ยังไม่แก้)

- ฟอร์มสร้าง/แก้ประกาศ, ส่งข้อเสนอ, โปรไฟล์ฟรีแลนซ์, โปรไฟล์ลูกค้า, ส่งงาน, แจ้งปัญหา และกล่องจัดการบัญชีของแอดมิน ส่งฟิลด์ตรงกับ schema ของ backend ทุกฟิลด์ ข้อมูลที่กรอกถึงฐานข้อมูลจริง
- มีฟิลด์ที่ frontend ส่งเกินและ Pydantic ทิ้งเงียบ ๆ เพราะ schema ไม่ตั้ง `extra="forbid"`: `clientId` ตอนสร้างประกาศ, `freelancerId`/`jobId` ในตัวข้อเสนอ, `audience` ของแจ้งเตือน, `userId` ของธุรกรรม ไม่มีผลเสียตอนนี้ เพราะ backend ใช้ตัวตนจาก session แต่ถ้าสะกดชื่อฟิลด์ผิดในอนาคตจะไม่มี error เตือน
- ไม่ถึง backend โดยออกแบบ: ไฟล์แนบของข้อเสนอเก็บเฉพาะชื่อไฟล์ และหน้า Settings เก็บในเบราว์เซอร์ ทั้งสองมีข้อความบอกผู้ใช้อยู่แล้ว
- Frontend เรียก endpoint ที่ backend ยังไม่มี: `GET/POST /freelancers/{id}/reviews` (หน้าประวัติการจ้างเรียกตอนเปิดหน้า ยังไม่ได้ตรวจว่าจัดการ 404 อย่างไร), `PATCH /projects/{id}` (ไม่มีหน้าไหนเรียก), `POST /transactions/withdraw` (ปุ่มถอนเงินในหน้ารายได้)

### Logic ที่น่าสงสัย (อ่านจากโค้ด ยังไม่ได้แก้)

- จำนวนครั้งที่ขอแก้งานไม่ถูกบังคับในฐานข้อมูล: `request_work_revision` ไม่เทียบกับ `revisionPolicy.maxRevisions` ในข้อตกลงหรือ `maxRevisions` ของสัญญา (ค่าปัจจุบัน 2)
- สถานะโปรเจกต์ `cancelled` และ `disputed` ไม่มีโค้ดส่วนไหนตั้งค่า มีแต่ที่อ่าน จึงยกเลิกโปรเจกต์ไม่ได้ และ `successRate` ของฟรีแลนซ์ไม่มีทางลดลง event `DisputeOpened` ก็ไม่ถูกฟัง
- `approve_work` เปลี่ยนสถานะใน DB อย่างเดียว escrow ยังเป็น `funded` (ยืนยันด้วย `flow_trace.py`) และไม่ตรวจว่าข้อตกลงยัง `funded` อยู่ ถ้าถูกคืนเงินไปแล้วยังกดอนุมัติได้
- งานแบบ `hourly`: การจ้างตั้ง `project.budget` เป็น `bid_amount` และ escrow ใช้ยอดนี้เป็นค่าจ้างทั้งโปรเจกต์ ทำให้ราคาต่อชั่วโมงถูกตีความเป็นยอดรวม
- ข้อเสนอไม่ถูกเทียบกับช่วงงบของประกาศ ยื่นสูงกว่า `budgetMax` ได้
- ระงับบัญชีลูกค้าแล้ว ประกาศที่เปิดอยู่ของบัญชีนั้นยังแสดงสาธารณะและรับข้อเสนอต่อ เพราะ `job_query` ไม่กรองสถานะผู้ใช้
- แอดมิน: `provision_admin` รับรหัสผ่าน 6–128 ตัว แต่ข้อความใน CLI และ README ระบุ 15–128 ตัว
- แอดมิน: การล็อกบัญชีหลังรหัสผิด 5 ครั้งนับต่อบัญชี ไม่จำกัดตามที่มา ผู้ที่รู้ username จึงล็อกบัญชีแอดมินเป็นช่วง ๆ ได้
- หน้า Admin: `GET /admin/overview` ส่งผู้ใช้ ประกาศ และรายงานทั้งหมดโดยไม่แบ่งหน้า ป้ายแท็บ "รายงานปัญหา" นับทุกรายการแต่การ์ดด้านบนนับเฉพาะที่ยังเปิด และมีโค้ดแสดงสถานะ `pending` ซึ่ง backend ไม่มี
- ข้อความภายในหลุดถึงผู้ใช้: หน้า `/how-it-works` ("รอข้อมูลจากทีม SMART CONTRACT"), ข้อความเก่าที่ยังบอกว่าสัญญา "ยังรอ/ในอนาคต" ในหน้ารายละเอียดงาน หน้าสมัคร และ `FreelancerProfile.jsx`

## 23 พฤศจิกายน 2026 · สรุปโครงการในเคสของแอดมิน

- เพิ่มปุ่ม **ดูสถานะโครงการ** ใน ticket ที่ยังเปิดและผูกกับโครงการ แสดงกำหนดส่ง สถานะ Escrow รายงวด และสถานะกับเวลาส่งงานล่าสุด แบบอ่านอย่างเดียว
- รายการธุรกรรมที่รอตรวจแสดงแยกจากยอดฝากที่ยืนยันแล้ว สรุปส่งเฉพาะสถานะและยอดงวด โดยเก็บไฟล์งานและแชตไว้ในหน้าของคู่สัญญา
- Migration `0012` เพิ่มตาราง `support_project_accesses` สำหรับบันทึกแอดมิน เคส โครงการ เวลา และ request ID ทุกครั้งที่เปิดสรุปสำเร็จ รายการ `event=support_project_viewed` ใช้ request ID เดียวกับ request log ของ API
- `alembic check` และ Frontend build ผ่าน ทดสอบ Backend บน PostgreSQL ผ่าน 13 รายการ รวมสถานะรอตรวจสอบ สิทธิ์เปิดสรุป การปิดเคส และความตรงกันของ request ID กับบันทึกการเข้าถึง อัปเดตฐานข้อมูลและตรวจ `/health` หลังเปิด API ในเครื่องแล้ว

## 21 พฤศจิกายน 2026 · FastAPI และ Marketplace

### งานที่เสร็จ

- เปิด PostgreSQL 17 สำหรับพัฒนาในเครื่องผ่าน Docker Compose ข้อมูลเก็บใน Docker volume และใช้ Alembic จัดการ schema
- เพิ่ม migration `0002` สำหรับตาราง `login_sessions` และชื่อไฟล์แนบของข้อเสนอใน `proposals.attachments`
- เพิ่ม Google OpenID Connect redirect และ callback, `GET /auth/me` และ `POST /auth/logout` ใช้ session cookie แบบ `HttpOnly` และเก็บ hash ของ session token ใน PostgreSQL
- เพิ่ม REST API สำหรับอ่าน สร้าง แก้ และลบงาน ส่ง ดู และถอนข้อเสนอ และสร้างโปรเจกต์เมื่อจ้าง API ใช้ session ตรวจเจ้าของข้อมูล และตรวจ origin สำหรับคำขอที่แก้ข้อมูล
- ทำการจ้างแบบ transaction โดยล็อกแถวของงานก่อนเลือกข้อเสนอ ถ้ากดจ้างข้อเสนอเดิมซ้ำจะได้โปรเจกต์เดิม เมื่อจ้างงานสำเร็จ ข้อเสนอที่ยังรอผลจะเปลี่ยนเป็น `rejected`
- เพิ่ม request log ที่มี request ID, HTTP method, route template, status และเวลาที่ใช้ API ส่ง request ID กลับใน `X-Request-ID` เพื่อใช้ตามรายการใน log

### ผลการทดสอบ

- รัน migrations จนถึง `0002` กับ PostgreSQL และตรวจ schema ด้วย `alembic check`
- ทดสอบบนฐานข้อมูล PostgreSQL ชั่วคราวตั้งแต่สร้างงานร่าง ลงประกาศ ส่งข้อเสนอ จ้าง และเปิดโปรเจกต์ ตรวจว่าบัญชีอื่นอ่านข้อมูลส่วนตัวหรือแก้ไขงานไม่ได้
- ทดสอบจ้างสองข้อเสนอพร้อมกัน ได้ HTTP `200` หนึ่งรายการและ `409` หนึ่งรายการ จากนั้นกดจ้างข้อเสนอเดิมซ้ำแล้วได้ project ID เดิม
- ทดสอบว่า session ใช้งานกับ `/auth/me` และถูกยกเลิกหลัง logout การทดสอบสร้าง session ในฐานข้อมูลชั่วคราว ส่วนการยืนยันผ่านบัญชี Google จริงต้องตั้ง OAuth credentials ก่อน

### งานที่เหลือหลังรอบแรก

- ต่อ Google Login และ cookie session กับ React แล้วทดสอบด้วยบัญชีจริง
- เพิ่ม Wallet verification, ข้อตกลงสำหรับ escrow และตรวจ event ของสัญญา Sepolia เส้นทางโปรเจกต์ปัจจุบันคืน `escrowStatus: unfunded` และไฟล์แนบข้อเสนอเก็บเฉพาะชื่อไฟล์ที่ frontend ส่งมา

## 22 พฤศจิกายน 2026 · ต่อ React กับ REST API

- เอาสวิตช์ mock และการโหลด session จำลองออกจาก React ตั้ง Axios ให้ส่ง session cookie และโหลดผู้ใช้จาก `GET /auth/me` หลัง Google redirect และเมื่อเปิดเว็บใหม่
- ย้ายข้อมูลและ services จำลองไปที่ `tests/fixtures/` เอารีวิว ตัวเลข และตัวอย่างธุรกรรมออกจากหน้าแรก แยก FAQ ที่เป็นคำอธิบายจริงไว้ใน frontend
- หน้า jobs, proposals และ projects อ่าน FastAPI โดยตรง หน้าแรกโหลดประกาศงานแยกจากไดเรกทอรีฟรีแลนซ์ Endpoint ที่ยังไม่มีจะแสดงข้อความว่าเซิร์ฟเวอร์ยังไม่เปิดฟีเจอร์นั้น
- ตรวจ `npm run build` และค้นหา marker ของ mock ใน bundle แล้วไม่พบ ทดสอบ import fixture แยกและรันชุดทดสอบ Marketplace กับ PostgreSQL ผ่าน
- ตรวจ FastAPI ที่รันจริงแล้ว `GET /jobs` พร้อมตัวกรองและ Origin ของ React ได้ HTTP `200` กับ CORS สำหรับ session cookie ส่วน Google Login ได้ `503` ระหว่างที่ OAuth credentials ยังไม่ครบ และ `GET /freelancers` ยังได้ `404`

- เปลี่ยนหมวดหมู่เป็นสายพัฒนาซอฟต์แวร์ 6 หมวด คง id `development`, `design`, `data` เดิมไว้ ส่วน `writing`, `marketing`, `video` ไม่ถูกเสนอให้เลือกแล้วแต่ยังแสดงชื่อในประกาศเก่า ทักษะแนะนำแยกตามหมวดอยู่ใน `src/constants/index.js` และช่องระยะเวลาเป็น dropdown พร้อมตัวเลือก "อื่น ๆ" ที่พิมพ์เองได้ (backend ยังรับข้อความอิสระ)

- เพิ่ม migration `0009` สำหรับข้อตกลงและผลตรวจธุรกรรม คู่สัญญาอ่าน JSON ต้นฉบับชุดเดียวกัน ซึ่งรวม Wallet ที่ยืนยันแล้ว แผนงวด รายการตรวจรับ ยอด wei, deadline และ ToS การกดเตรียมซ้ำคืนรอบปัจจุบัน และการฝากใหม่หลังคืนเงินใช้รหัสรอบใหม่

- เพิ่ม `app.escrow_worker` สำหรับค้นหา event จากรอบฝากเดิมแม้ยังไม่มีผู้ส่ง hash พร้อมบันทึกจุดอ่านต่อ รองรับการยืนยันฝากเงิน ปล่อยเงิน คืนเงิน และการปิดข้อพิพาทบน v2 โปรเจกต์สะท้อนสถานะงวด และหน้า Wallet อ่านประวัติธุรกรรมที่ยืนยันแล้วจาก API
- หน้า Escrow ของทั้งสองฝ่ายแสดงและดาวน์โหลดข้อตกลงได้ React คำนวณ `termsHash` ซ้ำและใช้ยอดจาก FastAPI ส่วนค่าธรรมเนียมอ่านด้วย `quote` ก่อนขอให้ MetaMask เซ็น เพิ่มการแสดงเลขธุรกรรมและการส่งเลขมาตรวจซ้ำ
- รัน migration แล้ว เปิด Uvicorn และ worker ในเครื่อง `GET /health` ตอบว่า PostgreSQL พร้อมใช้งาน ทดสอบ backend ผ่าน 12 เคส รวม receipt ที่ยังไม่ finalized, hash ของบล็อกไม่ตรง, ยอดใน event ไม่ตรง, เปิดงวดถัดไปหลังจ่าย และฝากรอบใหม่หลังคืนเงิน `alembic check`, `pip check` และ `npm run build` ผ่าน อ่าน `quote` และค่า policy จากสัญญา v2 จริงบน Sepolia สำเร็จ รอบนี้ใช้ receipt จำลองในเทสต์และยังไม่ได้เซ็นหรือส่งธุรกรรมจริงจากเบราว์เซอร์
- หน้าเตรียมข้อตกลงงวดเดียวมีตัวเลือกตามจำนวนวันที่ฟรีแลนซ์เสนอ โดย backend คำนวณกำหนดส่งจากตอนเตรียมและเก็บเป็นเวลาคงที่ ผู้จ้างยังเลือกเวลาเองได้ และต้องระบุเวลาของแต่ละงวดเมื่อแบ่งจ่ายหรือเริ่มรอบฝากใหม่ ปฏิเสธวันที่ย้อนหลังและคงกติกาขั้นต่ำ 7 วันทั้งฟอร์มและ API ปรับข้อความในหน้าผู้สมัครให้ตรงกับการจ้างที่บันทึกจริงใน PostgreSQL และเพิ่มลิงก์ตรงไปยังหน้า Escrow
